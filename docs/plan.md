# STARK 101 実装計画

FibonacciSqを題材に、Rustでトレースの生成からSTARK証明の検証までを段階的に実装します。全5段階を実装済みです。[実行手順と全体図](../README.md)

## ソースコードのコメント方針

公開する関数や型には、役割、入力と出力、呼び出し側が守る前提を日本語のRustdocコメント（`///`）で記述します。数学やプロトコルの理解に必要な箇所には、スライドの式とコード上の変数の対応、処理の理由、順序を守る理由を短いコメント（`//`）で説明します。

| 段階 | コメントで説明すること |
| --- | --- |
| トレース・LDE・Merkle木 | 二乗ごとに剰余を取る理由、`trace[i]` と `f(g^i)` の対応、拡張した評価領域に元の点を含めない理由 |
| 多項式制約 | 各分子・分母がどの制約を表すか、遷移が添字1020までで終わる理由 |
| FRI | `x` と `−x` から偶数次・奇数次の成分を取り出す式と、折り畳むと次数上限が下がる理由 |
| 証明と検証 | 何をハッシュに取り込んでからチャレンジを導くか、検証者が各開示値をどのrootと照合するか |
| 測定 | 証明サイズに含めるデータと、検証時間の計測範囲 |

各段階のレビューでは、該当するコメントを読んでスライドの式をコード上で追えることを確認します。数式や処理順を変更したときは、対応するコメントも同時に更新します。

## 各段階の実装内容と完了条件

### 1. トレースを多項式として固定する

実装済みの1,023項を、位数1,024の元 `g` を使い、点 `g^i`（i = 0〜1022）の値として並べます。これらを補間すると次数1,022以下の多項式 `f` が一意に決まります。次に、元の点と交わらない8,192点の乗法剰余類で同じ `f` を評価します。これが低次数拡張（LDE）です。評価値を葉とするMerkle木を作り、rootを公開します。

有限体演算、補間・評価、Merkle木の順で実装します。完了条件は、元の全点でトレースが復元できること、LDEの各葉に対する認証が通ること、葉を1つ変更すると元のrootに対するその葉の認証が失敗することです。[Part 1 · Statement, LDE and Commitment](https://starkware.co/wp-content/uploads/2021/12/STARK101-Part1.pdf)

### 2. 数列の規則を多項式の割り切れ方に変換する

初項の条件 `f(1) = 1` は、`f(X) − 1` が `X − 1` で割り切れることと同じです。末尾と漸化式にも同じ考え方を使います。

| 条件 | 分子 | 分母 |
| --- | --- | --- |
| 初項 | f(X) − 1 | X − 1 |
| 末尾 | f(X) − 2338775057 | X − g¹⁰²² |
| 遷移 | f(g²X) − f(gX)² − f(X)² | i = 0〜1020 の (X − gⁱ) の積 |

最後の遷移は第1,021項（添字1020）から末尾を見るので、分母の積もそこで止まります。トレースのrootを固定してから3つの係数を導き、各商に係数を掛けて足した合成多項式（CP）の評価表を固定します。正しいトレースでは各除算の余りがゼロで、CPの次数は最大1,023です。テストでは途中の1項だけを変更し、遷移制約の余りがゼロでなくなることも確かめます。[Part 2 · Polynomial Constraints](https://starkware.co/wp-content/uploads/2021/12/STARK101-Part2.pdf)

### 3. FRIで低次数性を検査する準備をする

多項式を偶数次と奇数次に分けると `P(X) = E(X²) + X O(X²)` と書けます。点 `x` と `−x` の値があれば、和と差から `E(x²)` と `O(x²)` を求められます。層のrootを固定してからチャレンジ値 β を導き、次の層の値を `E(x²) + β O(x²)` とします。各回で評価点の数が半分になり、次数の上限も半分（端数切り捨て）になります。

まず小さな既知の多項式で、係数から計算した次層と評価値のペアから作った次層が一致することをテストします。本実装ではCPとトレースの両方の次数を検査するため、初期層に `CP + γ₀·f + γ₁·X·f` を使います。次数上限1,023から10回折り畳むと、残る8点の値がすべて同じになります。[Part 3 · FRI Commitment](https://starkware.co/wp-content/uploads/2021/12/STARK101-Part3.pdf)

### 4. 証明を生成し、独立した検証者で読む

証明者は公開命題、各root、最終定数を決まった順でハッシュに取り込みます。各段階でそれまでの履歴から係数や問い合わせ位置を導く方法がFiat–Shamir変換です。証明には問い合わせへの応答として、トレースの3点 `f(x), f(gx), f(g²x)`、CPの開示値、FRI各層のペア、それぞれのMerkle認証経路を含めます。

検証者の入力は公開命題と証明です。検証者自身が同じ履歴からチャレンジを再現し、認証経路、3点から再計算したCP、折り畳み結果と次層の値、最後の定数まで順に照合します。完了条件は、証明を別プロセスで検証できること、公開した末尾・認証経路・最終定数を個別に変更したテストで拒否できることです。[Part 4 · The Proof](https://starkware.co/wp-content/uploads/2021/12/STARK101-Part4.pdf)

### 5. 証明の大きさを測る

同じ問い合わせ数でトレース長を変え、証明全体のバイト数、そのうち認証経路が占めるバイト数、検証時間を記録します。次にトレース長を固定し、問い合わせ数だけを変えます。どの条件で経路の長さが変わり、どの条件で経路の本数が変わるかを測定表から説明できれば完了です。[Finale · Review and Food for Thought](https://starkware.co/wp-content/uploads/2023/09/Stark-101-Finale.pdf)

## 次の実装計画 · ゼロ知識性を備えたFibonacciSqの証明

既存の `prove`・`verify` を使ってSTARK 101を学べる状態を保ち、同じFibonacciSqの公開命題を検証する `prove-zk`・`verify-zk` を追加する計画です。検証者は公開された末尾と証明ファイルを受け取り、証明者は第2項を別の入力として読み取ります。ゼロ知識性の対象は、第2項と途中の計算について、公開命題だけから得られる以上の情報を証明から明かさないことです。既定の第2項 `3141592` は教材で公開済みなので、実行例では別の値を使えるようにします。

### 実装で採用した構成

実行できるゼロ知識版にはTriton VM 9.0.0を使い、FibonacciSqの制約を固定プログラムに記述しました。証明のランダム化・DEEP・FRIはTriton VMが担います。以下は、教材用の証明器そのものをゼロ知識化する場合の設計案です。[実行手順](../README.md#ゼロ知識版で証明を生成する)

### 1. 参照プロトコルと保証範囲を決める

FRIベースのSTARKを対象とする *A Note on Adding Zero-Knowledge to STARKs* を設計の起点にします。最初に、論文の多項式IOPの定理が想定する評価領域、拡大体、商多項式の構成とマスク、DEEP評価、FRIの問い合わせ条件を表にし、FibonacciSqに適用する際に必要な変更を記録します。現行のFRIを再利用する箇所も、この対応を確認してから決めます。適用に必要なら、ゼロ知識版にDEEPによる整合性検査と商の分割を導入します。

多項式IOPの保証と、Merkle木・Fiat–Shamirで証明ファイルに変換した後の保証をそれぞれ確認します。参照構成が仮定するランダムオラクル、コミットメントの秘匿性、問い合わせ予算、有限体とチャレンジの大きさを設計メモに明記します。完了条件は、公開入力だけで検証者が見るデータをシミュレートできるという参照構成の論証を、採用する手順とパラメータに対応付けられることです。[多項式IOPとマスクの参照論文](https://eprint.iacr.org/2024/1037.pdf)・[STARK原論文](https://starkware.co/wp-content/uploads/2022/05/STARK-paper.pdf)

### 2. トレースをマスクし、次数を計算する

トレースを補間した後、その全点でゼロになる多項式 `Z_trace` と、証明ごとに暗号学的乱数から生成する多項式 `R` を使い、`f̃ = f + Z_trace·R` を作ります。元のトレース点では `f̃ = f` なので、初項・末尾・漸化式はそのまま成立します。トレース外では、LDEの評価表に乱数の影響が出ます。テストでは乱数源を注入し、結果を再現できるようにします。

現行のトレース配置を使うと、台のサイズ `N` に対して実際のトレース点は `N − 1` 個です。`R` に `b` 個の係数を使うと、`f̃` の次数上限は `D = N + b − 2` です。従って、2つの境界制約の商は高々 `D − 1` 次、二次の遷移制約の商は高々 `2D − (N − 3)` 次になります。この計算を出発点に、商の分割やマスクも含めてFRIが実際に検査する次数と評価領域を決めます。マスク係数の個数は、直接開示するトレース値だけでなく、参照構成で必要となるFRIの折り畳み元の点やDEEPの開示も数えて決定します。

完了条件は、複数の乱数でマスクしても全トレース点が保存され、トレース外の値が変化することと、実測した各多項式の次数が設計上限に収まることです。

### 3. 証明全体の開示を設計し、証明者と検証者を実装する

証明者がコミットする評価表、商の開示値、FRI各層のペアと最終出力を列挙し、開示の組み合わせからトレースを復元できないよう参照構成のマスクを適用します。元の制約との整合性も検証できるよう、マスクした商の検査とFRIの次数検査をつなぎます。コミットメントの秘匿に葉の乱数が必要な構成では、葉ごとに独立した乱数を生成し、開示した葉の認証に使います。

有限体演算とFibonacciSqの計算規則は現行実装を利用します。新しい証明形式には識別子とバージョンを設け、Fiat–Shamirの履歴にプロトコル識別子、公開命題、公開パラメータを取り込みます。検証側では、公開設定から開示数や認証経路の長さを決めて読み取ります。

### 4. 検証と教材を更新する

- 同じ第2項で複数の証明を作り、証明バイト列は異なり、それぞれ別プロセスで検証できることをテストします。
- 誤った公開値、改変した開示値・認証経路・FRI最終出力、異なる証明形式を拒否することを確かめます。既存の証明ファイルとCLIの回帰テストも実施します。
- 小さな有限体とトレースで、指定した問い合わせに対するマスク済み開示の分布を比較します。これはマスク実装の回帰テストとして扱い、ゼロ知識性の確認は第1段階の論証との対応で行います。その対応を完了条件として `zk` の名称を公開します。
- READMEに、公開値と証明者だけが使う入力、マスク前後のトレース点とLDE点、証明・検証コマンドをMermaidで図解します。現行版との証明サイズ、生成・検証時間の差も計測します。ソースコードには、`Z_trace` の根、各次数上限の由来、コミットメントとチャレンジの順序を日本語のコメントで説明します。
